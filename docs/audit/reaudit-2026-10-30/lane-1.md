**How "a screen is needed" was judged (applied the same way to every row).** A route alone is enough only when the requirement's actor is IT/platform administration. When the actor is a shop role (owner, store manager, buyer, accountant, category or pricing person, warehouse staff), the action needs a screen the person can use; otherwise the feature exists only for someone who can call the API by hand. Each "no screen" finding below was checked by searching every app (`apps/**/src/*.ts`, `apps/**/web/*.js`), the store computer (`edge/store-edge/src`) and the store computer's relay map (`edge/sync-agent/src/http-transport.ts`) for the route's path, so a later checker can repeat it with one `grep`.

## Plain-English summary for the owner

The engines behind the first nine modules are built and the 2,400-odd automated tests for them pass. What is not finished is mostly **office pages**: about twenty things work on head office's server but have no button on any screen, so today only a programmer could use them. The most important ones for the store:

- **Offers.** You cannot set up a "buy one get one", "3 for ₹99", coupon or member price from any screen. The Offer tab on the Products page cannot start a new offer at all against the real system.
- **Taking an item out of the range.** The Merchandising page says "Taken out of the range" but does not actually record it anywhere.
- **Supplier bills with freight.** A bill that includes transport or other charges cannot be typed in; the system says the total does not add up.
- **Damaged-stock corrections from the handheld** cannot be approved from any screen.
- **New GST rates, bundles, substitutes, product details**, dated or zone prices, supplier contracts and rebate schemes, PO changes and cancellations, branch opening/closing, reorder levels: all need screens.
- **GitHub safety switch.** The main code branch is not locked. Your developer habit is good (everything goes through a pull request), but GitHub itself would allow a mistake through.

**What to check, and how (in the store or on the office PC):**
1. Products page → Offer tab: type a new offer name and prices, press Start. Today it will be refused. After the fix it should start and show at the till.
2. Merchandising page → Range: take an item out, then reload the page. Today the item is back. After the fix it stays out and appears as "saved".
3. Supplier bills → type a bill whose total includes freight. Today it is refused. After the fix the freight is added to the item cost.
4. On a handheld, raise a damaged-stock correction, then look for it on the office PC. Today there is nowhere to approve it.
5. Ask your developer to switch on GitHub branch protection for `main` (required checks and one review).

**Decision needed (choose one):**
- **A (recommended).** Build the missing office pages before the pilot, in this order: offers, range drop, bill freight, adjustment approval, then the rest. About 3–4 weeks of work; staff can then do everything from screens.
- **B.** Build only the four store-floor ones (offers, range drop, bill freight, adjustment approval) before the pilot (about 1 week), and name a later release in writing for the rest. Until then your IT custodian does those setups by hand.
- **C.** Hide the Range "take out" button and the Offer "Start" button until they are fixed (1 day), and decide the rest later. Nothing misleading is left on screen, but those jobs stay manual.
