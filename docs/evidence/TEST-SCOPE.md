# Test scope statement — v1 (5 October 2026)

**Version:** v1 · **Applies from:** the commit that carries this file · **Owner of this document:** the build session,
under the owner's program directive · **Why it exists:** the independent repository audit of 4 October 2026 found
that the test and gate documentation had drifted (GT-09), that some "E2E" labels proved a browser boundary rather
than the whole user-to-database journey (GT-08), and that the acceptance evidence was not kept per kind (PF-15).
This is the one place that states exactly which suites exist, where each is required to run, which ones skip
themselves when a capability is missing and how that skip is refused, what each kind of evidence proves and does
not prove, the rule that binds a maturity label to the kinds behind it, and the human gates that remain. The
machine-readable companion is `docs/evidence/evidence-ledger.md` (and `.json`), generated by
`scripts/evidence-ledger.mjs` from `docs/completion-status.json`, the test tree and the SP-10 register, and kept
current by CI.

The dated snapshot `docs/audit/STORE-E2E-STATUS-MATRIX-2026-09-30.md` is **superseded history** for status: it is
kept as the record of 30 September and is referred to by link, never updated. Current status lives in the ledger.

## 1. The suites, and where each is required to run

| Suite | Command | Config | What runs | CI job (all required for a release) | Capability it needs | How a quiet skip is refused |
|---|---|---|---|---|---|---|
| Unit + guardrails | `pnpm run test` | `vitest.config.ts` | `tests/unit`, `tests/guardrails`, `tests/contract`, and every other `tests/**` file not claimed by another config | **Type check, lint, tests, secret & dependency scan** | none | — |
| Integration + migration on real PostgreSQL | `pnpm run test:db` | `vitest.config.ts` | `tests/integration`, `tests/migration` (the files that need `DATABASE_URL` skip without one) | **Stage gate suites (real PostgreSQL)** | a PostgreSQL 16 service | `DB_TESTS_REQUIRED=1` makes `tests/migration/db-required-in-ci.test.ts` fail by name when the database is missing or unreachable |
| Container and stack | (workflow steps) | — | the API image refuses a bad configuration; the whole stack comes up; the public origin and the hosted-demo overlay answer as ADR-0018/0016 require | **The container builds, starts, and refuses a bad configuration** | Docker | the steps assert each outcome |
| Browser | `pnpm run test:e2e` | `vitest.e2e.config.ts` | `tests/e2e/*.e2e.ts` — real headless Chromium (`playwright-core`) drives the real screens (every file skips without a Chromium; two also need `DATABASE_URL`) | **Browser suites (real Chromium) — required, never skip** | the exact Chromium `playwright-core` pins, installed from its registry; PostgreSQL for the connected suite | `BROWSER_TESTS_REQUIRED=1` makes `tests/e2e/browser-required-in-ci.e2e.ts` fail by name when Chromium is missing or will not launch or `DATABASE_URL` is unset; `scripts/assert-suite-ran.mjs` refuses the run unless ≥ 60 files and ≥ 200 tests ran with nothing pending, skipped or todo |
| Performance | `pnpm run test:perf` | `vitest.perf.config.ts` | `tests/performance` — ratios (how a read scales from 200 to 20,000 rows; rows read per request), one file at a time | **Performance suites — required, never skip** | none | `assert-suite-ran.mjs` at ≥ 3 files / ≥ 30 tests |
| Static integrity | parts of `pnpm run test` and workflow steps | — | guardrails over files and configuration; secret scan; dependency audit; SBOM drift; sync-script `--check`; **evidence-ledger `--check`** | the first job | none | each refuses by name |

The whole gate a build session runs before a pull request is `pnpm run check` = typecheck, lint, secret scan,
`test`, `test:perf`, `test:e2e`. The release job (`Deploy the merged release to the demo box`) needs all five
verification jobs on the same merge commit; the merged commit deploys itself (ADR-0017).

## 2. The kinds of evidence, and what each proves

| Kind | A test is this kind when | It proves | It does NOT prove |
|---|---|---|---|
| **Unit** | it lives under `tests/unit` | an engine's rules in isolation, with fakes for everything around it | that the engine is reachable from a screen, a route or a device; that anything is stored |
| **Integration (in-process)** | it lives under `tests/integration`, `tests/migration`, `tests/security` or `tests/contract` | the real API or store-box assembly, in one process — routes, authorization, event sourcing, idempotency — usually over the in-memory event store | that PostgreSQL behaves the same; that a person at a screen can reach it |
| **Real PostgreSQL** | an integration test that needs `DATABASE_URL` | the same, on a real database: schema, append-only guards, row-level security, restarts, the stage gates | the screen |
| **Browser (stub cloud)** | it lives under `tests/e2e` | real Chromium driving the real screen: it opens offline, meets WCAG AA at its target bar, the words are right in both languages, the one primary action, the interaction budget, a write leaves the page to a stub or in-process cloud | that the cloud effect happened on PostgreSQL (GT-08: a browser/session boundary, not the whole journey) |
| **Browser (connected)** | a browser test that also needs `DATABASE_URL` | the screen, the real store box and the real cloud on PostgreSQL in ONE run — the user-to-database journey | that a store worker on the store's own hardware gets the same result |
| **Device** | a PASS session in `docs/registers/sp10-staff-uat.md` on real hardware (`**Device:**` names it) | the store PC, scanner, printer or phone in the store's hands | nothing about code paths the session did not walk |
| **Staff UAT** | a PASS session in the SP-10 register | a named person did the work and signed what they saw | — |

A guardrail (`tests/guardrails`) proves a property of the files and configuration — it is a control, never evidence
that a requirement works, and the ledger does not count it. A performance test proves a ratio, not a requirement.

## 3. Capability-dependent skips, and what refuses them

Every browser file begins `describe.skipIf(!HAVE_BROWSER)`; two add `|| !DATABASE_URL`. Every database-backed
integration or migration file begins `describe.skipIf(!DATABASE_URL)`. On a laptop without the capability the suite
reports "skipped" and that is correct. In the required CI jobs the same skip would be a false green, so the jobs set
the REQUIRED flags above and end with `assert-suite-ran.mjs`; a missing capability fails the job by name. The one
remaining way a browser test can be skipped in CI is to delete it — the file floor catches a wholesale deletion, the
guardrail on the workflow catches a lowered floor.

## 4. The label rule — what a maturity label needs before it may be claimed

The completion model's ladder is `NOT_STARTED · ENGINE_ONLY · PARTIALLY_WIRED · WIRED · INTEGRATION_TESTED ·
E2E_VERIFIED · UAT_VERIFIED · PRODUCTION_VERIFIED` (`docs/COMPLETION-MODEL.md`). From v1 of this statement a
label is allowed only when the item has the kinds below, as derived by `scripts/evidence-ledger.mjs`
(`labelHolds`), and CI fails when it does not:

| Label | Needs |
|---|---|
| up to `WIRED` | no evidence kind here; `tests/guardrails/completion-ladder-has-evidence.test.ts` holds WIRED+ to a registered, existing file |
| `INTEGRATION_TESTED` | ≥ 1 integration test (in-process or real PostgreSQL) citing the requirement |
| `E2E_VERIFIED` | ≥ 1 integration test **and** ≥ 1 browser test (the user boundary) **and** ≥ 1 real-PostgreSQL test or connected browser test (the cloud effect). When the cloud effect comes from a separate run, the ledger says so ("separate runs"); only a connected browser test proves the journey in one run |
| `UAT_VERIFIED` | all of the above **and** ≥ 1 PASS session in the SP-10 register covering the requirement |
| `PRODUCTION_VERIFIED` | not claimable under v1 — no production evidence kind is defined yet |

A test cites a requirement when its text names the ID (M12 or M12-FR-nn, D04, WF-10, QG-05, A06, MG-04), or when the
ledger item's evidence prose names the test file by path (the stage-gate suites cite roadmap stages, so the ledger
records which gate proves which requirement). **Labels move only on proof:** a label the rule refuses is moved down
in `docs/completion-status.json` with the reason, and the mirrors in `docs/traceability.md` follow (their guardrails
refuse drift).

## 5. The human gates that remain, by name

| Gate | What only a person can do | Where it is recorded |
|---|---|---|
| Device acceptance | run the practice script on the store PC, scanner, printer and phones | `docs/registers/sp10-staff-uat.md` — 0 sessions at v1 |
| Staff acceptance | a named buyer, receiver, back-store worker, floor receiver, cashier and manager sign what they saw | the same register |
| Live providers | payment, GST portal, messaging and the production identity provider need credentials and certification (OA-4, EX-03) | `docs/OWNER-ACTION-REGISTER.md`; ADR-0019 for identity |
| Production | a real tenant on a real domain with real data | not started; synthetic data only until a written Option 2 GO |

## 6. How to read the ledger

`docs/evidence/evidence-ledger.md` has one row per controlling requirement: the label, a count per kind, and
whether the label holds with the reason. The section after the table names the browser, connected and
real-PostgreSQL files behind each row; the JSON twin lists every file. Regenerate with
`node scripts/evidence-ledger.mjs`; CI runs `--check` on every build and fails on drift or on a label that outruns
its proof.
