# M02 — Identity, RBAC and approvals

- **Priority:** P0 (architectural/security foundation) · **Release:** R1 · **Stage:** 7 (engine built in Stage 5)
- **Roadmap source:** §5 M02; cross-cutting §9.1 (SEC), §28 (separation of duties), §31, §34, §35
- **Purpose:** Who may do what, where, up to what value, in which state — and how sensitive actions get a second pair of eyes. This is the control that makes "control by exception" (P-03) and "secure by design" (P-04) real. **No shared logins, ever** (§3 access rule, hard rule #4).

> Each requirement expands a roadmap FR into the Appendix B record. Store-fact
> gaps are marked `⟳ AVR-##`. All requirements inherit the §5 cross-cutting
> standard. Guardrail `tests/guardrails/shared-login.test.ts` already enforces the
> no-shared-login rule at the code level.

## M02-FR-01 — Users, authentication and sessions

- **Statement:** The system shall provide unique named user accounts with MFA/passkey readiness, session management and an enforced password policy; no account may be shared.
- **Business reason:** Every action must be attributable to a real person; shared logins destroy accountability and are a top audit finding (A-17/AVR-08).
- **Actors & scope:** Security Admin/Platform Admin (provision), every user (authenticate), Auditor (review).
- **Preconditions:** Organizational hierarchy exists (M01-FR-01).
- **Main flow:** Admin creates a named user → assigns roles/scope (FR-02) → user sets credentials and enrols MFA/passkey → user authenticates → session issued with timeout.
- **Alternate / error flows:** Failed logins lock per policy; expired/locked sessions require re-auth; MFA failure blocks access; a disabled user cannot authenticate.
- **Business rules:** One identity per person; MFA required for privileged and remote access (SEC-03); password policy (length, reuse, rotation) enforced; sessions expire on inactivity and are device/branch-bound where applicable (§28 "assigned terminal/till"); credentials are never stored in plain text and never logged (SEC-04, hard rule #4).
- **Permissions / approval:** Only Security/Platform Admin provisions users; admins cannot grant themselves business-approval authority (§28).
- **Offline / sync (§31):** POS uses a **limited cached identity** for authorized offline operators (API-01 "limited cached POS identity"); cached credentials are minimized and time-bound; new users/permission changes take effect on next sync; revocation propagates as a priority sync.
- **Audit / privacy / security:** Every login, logout, lock, MFA event and admin change audited immutably (M34-FR-01); auth events are tamper-evident (SEC-07); personal data (name, contact) classified and access-controlled (PRV-01).
- **Integration / reporting:** API-01; access-review report lists users, roles, scope and last login.
- **Acceptance criteria:** A shared/generic account cannot be created (guardrail + server rule); MFA can be enrolled and is required for an admin; a locked-out user is blocked and the event is in the audit log; an offline lane authenticates an authorized cashier with the network cable out.

## M02-FR-02 — Authorization: role, branch, department, value-limit and state

- **Statement:** The system shall authorize every action by role plus branch/department scope, value limit, transaction state and purpose, enforced on the server — never only hidden in the screen.
- **Business reason:** Least privilege (P-04, SEC-03); a cashier must not price-change, a manager must not approve their own adjustment (§28).
- **Actors & scope:** Security Admin (define roles), all roles (constrained), Auditor (review). Roles per §28 SoD matrix.
- **Preconditions:** Users exist (FR-01); roles and value limits configured `⟳ AVR-08`.
- **Main flow:** Admin defines role → assigns permissions, branch/department scope, value limits and allowed states → assigns role to user → server enforces on every request.
- **Alternate / error flows:** An out-of-scope or over-limit action is denied server-side with a clear reason and audit entry; UI hides unavailable actions but the server is the authority (§35 "Deny server-side; UI hiding is not control").
- **Business rules:** Permissions constrained by company/branch/warehouse/department/function/value/state/time (§3); default deny; separation-of-duties pairs from §28 are enforced (e.g. requisition ≠ receive ≠ pay by the same user).
- **Permissions / approval:** Role changes are maker-checker and owner-approved for high-authority roles; an admin cannot widen their own scope.
- **Offline / sync (§31):** Effective permissions are cached at the edge for authorized operators; offline actions respect cached value limits and offline risk caps (§31 loyalty/refund limits); permission changes apply on sync.
- **Audit / privacy / security:** Every permission grant/deny for sensitive actions audited; access reviews supported (SEC-11).
- **Integration / reporting:** API-01; a permissions matrix export and an access-review report.
- **Acceptance criteria:** A cashier attempting a price change is denied on the **server** (verified by calling the API directly, not just the hidden button); a user scoped to Branch A cannot read Branch B data via the API; an over-limit discount is blocked and audited.

## M02-FR-03 — Maker-checker approval engine, delegation and escalation

- **Statement:** The system shall provide a reusable maker-checker approval engine with configurable thresholds, delegation and escalation, usable by every module that requires approval.
- **Business reason:** Approvals are pervasive (purchase, price, refund, adjustment, config); one governed engine ensures consistency and evidence (P-03, P-04).
- **Actors & scope:** Any maker (submit), authorized checker/approver (decide), Owner (top of escalation).
- **Preconditions:** Roles and value limits exist (FR-02).
- **Main flow:** Maker submits an action needing approval → engine routes to the authorized checker by scope/value → checker approves/rejects with reason → action commits or is discarded → evidence recorded.
- **Alternate / error flows:** No eligible approver → escalate per rules; approver unavailable → delegate; pending approval invalidated if the underlying object materially changes (§31.1 "material change invalidates pending approval"); timeout escalates.
- **Business rules:** A maker can never approve their own request (§28); approval authority is bound to value limits and object version; delegation is time-bound and logged; deterministic rules — not AI — commit the action (P-05); AI may only draft (AI-NFR-12).
- **Permissions / approval:** Approver authority from FR-02; delegation requires the delegator's authority and is auditable.
- **Offline / sync (§31):** Approvals are generally online; where an offline supervisor override is permitted (e.g. POS), it follows explicit offline rules and reconciles on sync; a stale offline approval for a changed object is rejected.
- **Audit / privacy / security:** Every submit/approve/reject/delegate/escalate recorded immutably with reason and object version (M34-FR-01); AI-drafted actions are labelled and still require human approval (AI-NFR-07/12).
- **Integration / reporting:** API-01; an approvals report (pending, aged, approver, outcome) feeds the owner approval inbox (M29-FR-03).
- **Acceptance criteria:** A maker cannot approve their own request; changing the amount of a pending request invalidates its approval; an aged pending approval escalates; every decision has a reason and is auditable.

## M02-FR-04 — Joiner, mover, leaver and emergency access

- **Statement:** The system shall manage the full access lifecycle — joiner (grant), mover (re-scope), leaver (revoke) — plus controlled, time-bound, audited emergency access.
- **Business reason:** Orphaned access and lingering ex-staff logins are a major security and fraud risk (M15, SEC-11); access must track employment reality.
- **Actors & scope:** Security/Platform Admin (execute), Store/HR manager (request/confirm), Owner (approve emergency access).
- **Preconditions:** Users and roles exist (FR-01/FR-02).
- **Main flow:** Joiner — request → approve → provision scoped access → user active. Mover — change branch/role → re-scope → old scope removed. Leaver — trigger → revoke all access, close sessions, reassign ownership. Emergency — request → owner approval → time-bound elevated access → auto-expire → review.
- **Alternate / error flows:** A leaver with owned open items must reassign before completion; emergency access auto-expires and cannot be silently extended (SEC-11); a mover never accumulates old + new scope.
- **Business rules:** Access equals current role/branch only; emergency/privileged access is time-limited, recorded and reviewed (SEC-11 "no perpetual support access"); revocation is immediate and propagates to the edge as priority sync.
- **Permissions / approval:** Owner approves emergency/privileged elevation; separation between requester and granter (§28).
- **Offline / sync (§31):** Revocation propagates to stores on next sync as a priority item; edges cache a short-lived permission set to bound exposure.
- **Audit / privacy / security:** Every lifecycle event and every emergency-access session recorded immutably (session logging, SEC-11); leaver revocation evidenced.
- **Integration / reporting:** API-01; access-review and emergency-access reports (who, when, why, duration).
- **Acceptance criteria:** A leaver's access is fully revoked and sessions closed; emergency access expires automatically at its limit; a mover no longer has their old branch's access; every emergency grant shows approver, reason and duration.

## Module acceptance & test families
- **Security/RBAC (QG-06):** server-side enforcement proven by direct API calls; cross-branch data isolation; no shared login (guardrail-enforced).
- **Approvals:** maker≠checker; version-bound invalidation; escalation on timeout.
- **Offline (§31/QG-04):** authorized cashier authenticates offline; revocation applies on sync; offline override rules honoured.
- **Audit (NFR-15):** every auth and approval event reconstructable from immutable evidence.
- **Lifecycle:** joiner/mover/leaver/emergency each tested including the failure paths.
