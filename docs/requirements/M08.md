# M08 — Inventory ledger and availability

- **Priority:** P0/P1 · **Release:** R2 · **Stage:** 8 · **Roadmap:** §5 M08, §16 D05, §29 (Inventory), §31.1, §30.2
- **Purpose:** The one true record of stock. Every movement is an **append-only event**; the balance is *projected* from events, never overwritten (hard rule #2, §31.1). This is what makes stock trustworthy across POS, orders and finance. Enforced in code by `tests/guardrails/ledger-append-only.test.ts`.

> Appendix B records; `⟳ AVR-##` marks store facts; §5 cross-cutting inherited. Related extension **D05** (perpetual event ledger & reconstruction, ownership status, reservation buffer).

## M08-FR-01 — Immutable movement ledger; stock by status/location/batch
- **Shall:** record every stock movement as an immutable, append-only event and project on-hand balances by status, location and batch from those events.
- **Actors/scope:** all stock-moving modules (receiving M07, POS M12, transfers M09, adjustments FR-03) write events; everyone reads projected balances. **Preconditions:** products (M03), locations (M04/M01).
- **Flow:** a movement (receive/sell/transfer/adjust/return) appends an event with qty, sign, location, batch, reason, source id → server projects the new balance. **Alt/error:** a correction is a **new compensating event**, never an edit; duplicate events collapse by idempotency id (§31.1).
- **Rules:** **no UPDATE/DELETE on the ledger** (hard rule #2, §29.1); balance = sum of events; every event carries a globally unique id and source reference; events are ordered deterministically.
- **Permissions (§28):** only authorized module actions append; no user edits history. **Offline (§31):** movement events append locally and sync idempotently; **conflicts become exceptions, not silent last-write-wins** (§31.1).
- **Audit/privacy:** the ledger *is* the audit for stock; events immutable (M34); `InventoryMoved` event (§30.2). **Integration/reporting:** API-04; stock-by-location/status/batch report.
- **Acceptance:** an attempt to update or delete a past movement row **fails** (roadmap Stage 8 test); replaying the same movement five times yields one balance change; the projected balance equals the sum of events after an offline day.

## M08-FR-02 — Stock states: on-hand, available, reserved, damaged, expired, quarantine, in-transit
- **Shall:** track stock by state so that only truly sellable stock is available, and reservations/quarantine/expiry are excluded per policy.
- **Actors/scope:** OMS (M18 reserves), receiving (M07 quarantine), expiry (M10). **Preconditions:** ledger (FR-01).
- **Flow:** an event sets/changes a unit's state → availability = on-hand − reserved − quarantine − damaged − expired (per policy). **Alt/error:** reserving more than available is blocked (no oversell, feeds M18 no-oversell gate).
- **Rules:** **reserved stock is excluded from sellable availability** (§6.2 omnichannel invariant); quarantine/expired/damaged never sellable; in-transit visible but not available at destination until received.
- **Permissions (§28):** state changes via authorized actions. **Offline (§31):** availability computed at edge from cached ledger; offline reservations follow risk caps.
- **Audit/privacy:** state transitions audited via events. **Integration/reporting:** API-04; availability and reserved-stock reports.
- **Acceptance:** an online order reservation removes stock from what a walk-in can buy (no oversell); quarantined/expired stock cannot be sold; in-transit is not counted as available until received.

## M08-FR-03 — Negative-stock controls, reason-coded adjustments and approval
- **Shall:** control negative stock, and require reason codes and approval for adjustments.
- **Actors/scope:** Warehouse/Manager (raise), Manager/Owner (approve). **Preconditions:** ledger (FR-01).
- **Flow:** adjustment proposed with reason code + value → approval by threshold → compensating event appended. **Alt/error:** negative on-hand blocked or flagged as an exception per policy; over-threshold adjustment escalates.
- **Rules:** adjustments are compensating events (never edits); reason codes mandatory; value impact recorded; **self-approval of material variance forbidden** (§28).
- **Permissions (§28):** adjustment approval above the raiser's authority. **Offline (§31):** adjustments queued; approval on sync.
- **Audit/privacy:** every adjustment audited with reason, value, approver; event `InventoryAdjusted`. **Integration/reporting:** API-04; adjustment and negative-stock reports.
- **Acceptance:** an adjustment cannot be posted without a reason code; a large adjustment needs approval; the raiser cannot approve their own material variance.

## M08-FR-04 — Ageing, turns, GMROI, stockout and reconciliation reports
- **Shall:** report stock ageing, turns, GMROI, stockouts and physical-to-system reconciliation.
- **Actors/scope:** Manager/Owner/Finance. **Preconditions:** ledger + cost (M07) + sales (M12).
- **Flow:** compute metrics from ledger + valuation → present with drill-through → reconcile against counts (M09-FR-04). **Alt/error:** unreconciled variance surfaces as an exception with value.
- **Rules:** valuation method consistent (feeds M23 inventory valuation); reconciliation differences explained and owned (P-08).
- **Permissions (§28):** report scope by role/branch. **Offline (§31):** reports use last-synced data with freshness shown.
- **Audit/privacy:** report parameters logged. **Integration/reporting:** API-04/API-10.
- **Acceptance:** a physical count reconciles to the ledger or the difference is explained and valued; ageing/turns/GMROI compute correctly against known data.

## Module acceptance & test families
- **Append-only proof (QG-07):** update/delete of a past movement fails; balance = sum of events; guardrail test enforced in CI.
- **Idempotency (§31):** replayed movement → one effect; out-of-order events → correct ordered result.
- **No oversell:** reservation excludes availability.
- **Offline (§31/QG-04):** movements append and reconcile after an offline day.
