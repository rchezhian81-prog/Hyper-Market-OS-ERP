- **Priority:** P1 (critical path to M5, 1 Apr 2027) · **Release:** R2 · **Stage:** 9 · **Roadmap:** §5 M12, §16 D04, §4.2, §31, §32, §35
- **Purpose:** The till you decided to build (OD-04). It must be **boringly reliable and fast**: sub-second scan, and a core cash sale that completes **with the network cable out** (hard rule #1). No card data ever touches us (hard rule #3). Enforced by `tests/guardrails/pos-offline.test.ts` and `card-data.test.ts`.

> Appendix B records; `⟳ AVR-##` marks store facts; §5 cross-cutting inherited. Related extension **D04** (LAN-first scan/weight/total, pending-payment recovery, peripheral health, self-checkout readiness). **Performance is a hard requirement, not an aspiration** (§32).

## M12-FR-01 — High-speed scan/search, quantity, weight, price enquiry, customer display
- **Shall:** scan or search items fast, handle quantity and weight, answer price enquiries, and drive a customer display — all from the local edge with no cloud round-trip.
- **Actors/scope:** Cashier (POS). **Preconditions:** product/price/tax cached (M03/M05, §31 full-offline class), lane configured (M01/M33).
- **Flow:** scan barcode (incl. variable-weight, M03-FR-02) or search → line added at correct price/promotion (M05) → quantity/weight adjusted → customer display updates. **Alt/error:** unknown barcode → fast search fallback; scale error → manual weight with supervisor rule.
- **Rules:** **no blocking network round-trip for a local core sale** (hard rule #1, NFR-02); price/promotion resolved deterministically from the local pack (M05); weight precision UOM-aware (§29.1).
- **Permissions (§28):** Cashier on assigned terminal; **cannot change prices**. **Offline (§31):** full offline from signed cache.
- **Audit/privacy:** line events captured for the sale; no personal data required to sell. **Integration/reporting:** API-05 (edge-first); scan-performance telemetry.
- **Acceptance (perf, §32/QG-05):** **scan-to-line p95 ≤ 300 ms on certified pilot hardware** — measured and shown; scanning works with the network cable out; a variable-weight item prices correctly offline.

## M12-FR-02 — Suspend/recall, quotations, receipts, delivery sales
- **Shall:** suspend and recall bills, produce quotations, issue digital/printed receipts, and support delivery sales.
- **Actors/scope:** Cashier. **Preconditions:** sale in progress.
- **Flow:** suspend bill → recall later → resume; convert quotation to sale; print/issue digital receipt; mark a sale for delivery (feeds M18). **Alt/error:** recall of another lane's suspended bill controlled by policy; receipt reprint controlled.
- **Rules:** a suspended bill is durable locally; receipts are generated from the committed sale (M31); quotations are non-committing until converted.
- **Permissions (§28):** cross-lane recall per policy. **Offline (§31):** suspend/recall/receipt fully offline.
- **Audit/privacy:** suspend/recall/reprint audited (loss-prevention signal, M15). **Integration/reporting:** API-05; suspended-bills report.
- **Acceptance:** a suspended bill survives a lane restart and can be recalled; a receipt prints offline; a quotation does not affect stock until converted.

## M12-FR-03 — Cash/card/UPI/store credit/split tender with explicit offline rules
- **Shall:** accept cash, card, UPI, store credit and split tenders, with explicit offline rules and **no invented approvals**.
- **Actors/scope:** Cashier; payment via certified provider terminal (D14). **Preconditions:** tenders configured; **RBI-authorized provider** (M23/§35).
- **Flow:** choose tender(s) → for cash, commit locally and print; for card/UPI, request provider auth → on success commit; **if uncertain, mark pending and reconcile — never assume approval** (§31, §4.3). **Alt/error:** provider timeout → pending state, recovery reconciles (D04-FR-02); split tender balances to total.
- **Rules:** **core cash sale never depends on the network** (hard rule #1); **durable local commit before the receipt is declared successful** (§4.2); globally unique immutable transaction id; idempotent sync (§31.1); **never store card number/CVV/expiry — provider tokens only** (hard rule #3, §35, SEC-12).
- **Permissions (§28):** Cashier; overrides via supervisor (FR-04). **Offline (§31):** cash/store-credit full offline; card/UPI provider-dependent, show pending/declined, reconcile; loyalty/store-credit offline caps prevent double-spend.
- **Audit/privacy:** tender events + `SaleCommitted`, `TenderAuthorized/Uncertain/Settled` (§30.2); **no card PAN/CVV anywhere in data or logs** (guardrail + SEC-12). **Integration/reporting:** API-05; tender and pending-payment reports.
- **Acceptance:** a cash sale completes and prints **with the network unplugged**; a card timeout produces a pending state that reconciles without double charge; the same sale replayed on sync produces one ledger effect; **no card number can be found anywhere in the system** (security test + guardrail).

## M12-FR-04 — Supervisor overrides, age/restricted prompts, lane health
- **Shall:** enforce supervisor overrides, age/restricted-item prompts, and monitor lane health.
- **Actors/scope:** Cashier + Supervisor. **Preconditions:** roles (M02), restricted flags (M03).
- **Flow:** restricted/age item → prompt → supervisor override where allowed → recorded; lane health (peripherals, sync, offline state) shown. **Alt/error:** override beyond supervisor authority escalates; unhealthy peripheral flagged.
- **Rules:** overrides are authorized and audited (loss-prevention, M15); age/restricted prompts mandatory for flagged items; lane shows **online/degraded/offline state and unsent count** (§27.1).
- **Permissions (§28):** override by Supervisor authority; cashier cannot self-override. **Offline (§31):** overrides follow offline supervisor rules; state visible.
- **Audit/privacy:** every override audited with reason and approver. **Integration/reporting:** API-05/API-11; override and lane-health reports.
- **Acceptance:** an age-restricted item prompts and blocks without override; an override is recorded with who approved it; the lane clearly shows offline state and the unsent-sale count.

## Module acceptance & test families
- **Offline (hard rule #1, QG-04):** pull the cable mid-basket → sale completes, prints, and later syncs exactly once.
- **Performance (§32/QG-05):** scan-to-line p95 ≤ 300 ms; total/tender p95 ≤ 500 ms (excl. external auth) — measured on certified hardware.
- **Payment safety (hard rule #3):** no card PAN/CVV/expiry stored or logged (guardrail + security test); pending never becomes a false approval.
- **Idempotency/durability (§4.2):** replay, out-of-order, power-cut-at-commit all yield one correct result.
