# M13 — Returns, exchanges and refunds

- **Priority:** P1 · **Release:** R2 · **Stage:** 9 · **Roadmap:** §5 M13, §29, §30.2, §31
- **Purpose:** Take goods back fairly and safely — with or without a receipt under policy — refund by the right method, and make sure every refund reconciles against the original payment (no leakage, no double refunds).

## M13-FR-01 — Receipt and controlled no-receipt returns
- **Shall:** process returns against an original receipt, and no-receipt returns under a controlled policy.
- **Actors/scope:** Cashier/Customer Service + Supervisor (no-receipt). **Preconditions:** original sale (M12) for receipted returns.
- **Flow:** locate original sale by receipt → select lines to return; or no-receipt → identify item, apply controlled policy + approval. **Alt/error:** no-receipt beyond policy limit blocked/escalated; already-returned line cannot be returned again.
- **Rules:** a line can be returned at most once (idempotent against the original); **no-receipt returns require supervisor approval and are capped** (loss-prevention, M15); returns link to the original tender for reversal (FR-04).
- **Permissions (§28):** no-receipt/high-value return approved above cashier. **Offline (§31):** receipted return works offline where the original is locally known; no-receipt follows offline supervisor rules; reversal queued and reconciled.
- **Audit/privacy:** every return audited; `ReturnAccepted` (§30.2). **Integration/reporting:** API-05; returns and no-receipt-return reports.
- **Acceptance:** the same line cannot be returned twice; a no-receipt return above policy is blocked without supervisor approval; a receipted return works with the network cable out and reconciles on sync.

## M13-FR-02 — Eligibility, reason, condition, serial/batch, disposition
- **Shall:** check return eligibility, capture reason and condition, record serial/batch, and set disposition (resell/quarantine/scrap).
- **Actors/scope:** Cashier/Customer Service. **Preconditions:** return started (FR-01).
- **Flow:** check eligibility (window/policy) → capture reason + condition + serial/batch → set disposition → stock event to the right state (M08). **Alt/error:** ineligible item blocked with reason; damaged item → quarantine/scrap, not resale.
- **Rules:** returned stock only re-enters availability if disposition = resell (M08 states); batch/serial preserved for traceability (M10); recall-blocked item handled per M10.
- **Permissions (§28):** disposition per authority. **Offline (§31):** capture offline; stock event queued.
- **Audit/privacy:** reason/condition/disposition audited. **Integration/reporting:** API-04/API-05; return-reason and disposition reports.
- **Acceptance:** a damaged return does not go back to sellable stock; an out-of-window return is blocked per policy; serial/batch is preserved through the return.

## M13-FR-03 — Exchange, refund method, store credit, approval thresholds
- **Shall:** support exchanges and refunds by the appropriate method (original tender, store credit), with approval thresholds.
- **Actors/scope:** Cashier + Supervisor/Manager (thresholds). **Preconditions:** eligible return (FR-01/02).
- **Flow:** choose exchange or refund → refund to original tender or store credit per policy → approve if above threshold. **Alt/error:** refund method not matching policy blocked; high-value refund escalates.
- **Rules:** refund defaults to original tender where possible; store credit issued with fraud limits (M17); **refunds above threshold require approval** (loss-prevention); an AI agent can never authorize a refund (AI-NFR-12).
- **Permissions (§28):** refund approval by threshold; cashier cannot self-approve high-value. **Offline (§31):** cash/store-credit refunds offline within caps; card reversal queued.
- **Audit/privacy:** refund method and approvals audited. **Integration/reporting:** API-05; refund and store-credit reports.
- **Acceptance:** a high-value refund needs approval; store credit issued respects fraud limits; a refund cannot exceed the original paid amount.

## M13-FR-04 — Payment reversal, gateway status, financial reconciliation
- **Shall:** reverse card/UPI payments via the provider, track gateway status, and reconcile refunds financially.
- **Actors/scope:** Cashier/Cash office/Finance. **Preconditions:** original tender (M12), provider (M23/§35).
- **Flow:** request provider reversal → track status (pending/success/failed) → reconcile against original payment and refund. **Alt/error:** failed reversal raises an exception; pending reversal never assumed complete (§4.3).
- **Rules:** every refund/reversal is independently reconcilable (§6.2); **never invent a reversal success** (mirror of the no-invented-approval rule); no card data stored (hard rule #3).
- **Permissions (§28):** finance reconciliation. **Offline (§31):** reversal is provider-dependent; queued and reconciled; customer told the true state.
- **Audit/privacy:** reversal status and reconciliation audited; `RefundCompleted/Failed` (§30.2). **Integration/reporting:** API-05/API-09; refund-reconciliation report.
- **Acceptance:** a card refund reconciles to the original charge; a failed reversal is an exception, not a silent success; refund totals reconcile at day close (M14).

## Module acceptance & test families
- Return idempotency (no double return/refund); no-receipt controls; damaged-goods disposition excludes resale; refund ≤ original; reversal reconciliation; offline receipted return.
