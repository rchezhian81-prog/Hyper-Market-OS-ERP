# M31 — Documents and notifications

- **Priority:** P1/P2 · **Release:** R2 (documents/receipts) → R4 (messaging) · **Roadmap:** §5 M31, §16 D14, §9.2 (consent), §28. **API-11.**
- **Purpose:** The shared engine for producing **documents** (receipt, invoice, PO, GRN, statement) and sending **notifications** (email/SMS/WhatsApp/push) — versioned templates with retention, consent-safe routing with delivery status, and retry/suppression/cost/approval controls. Cross-cutting: POS receipts (M12), purchase/finance documents, and CRM messaging (M21) all use it.

> Appendix B; §5 inherited. Builds on document templates (M01-FR-02), the messaging broker
> (§30.2) and consent (M16/PRV).

## M31-FR-01 — Versioned document storage, templates and retention
- **Shall:** store documents and templates as versioned records with retention.
- **Actors/scope:** All document-producing modules. **Preconditions:** templates (M01-FR-02).
- **Flow:** a template version renders a document → stored immutably with retention → old
  documents keep their original layout. **Alt/error:** a template change is a new version,
  never overwriting issued documents.
- **Rules:** templates versioned (M01-FR-03); documents immutable + retained (#6);
  per-tenant branding (M36-FR-02).
- **Permissions (§28):** template changes approved. **Offline (§31):** receipts render offline
  from the signed template pack.
- **Audit/privacy:** document/template versions audited. **Integration:** API-11; object storage.
- **Acceptance:** a template change produces a new version while issued documents keep their
  layout; retention holds.

## M31-FR-02 — Receipt / invoice / PO / GRN / statement generation
- **Shall:** generate receipts, invoices, POs, GRNs and statements from committed records.
- **Actors/scope:** POS (M12), Purchase (M06/07), Finance (M23). **Preconditions:** the
  committed source record + template + number series (M01-FR-02).
- **Flow:** a committed sale/PO/… → document generated with a gap-free number
  (`packages/numbering`) → printed/issued/stored. **Alt/error:** reprint controlled/audited
  (M12-FR-02).
- **Rules:** generated from the committed record (not a draft); exact money
  (`packages/contracts`); GST correct (M23).
- **Permissions:** per role; reprint controlled. **Offline (§31):** POS receipts print offline
  (hard rule #1).
- **Audit/privacy:** generation/reprint audited. **Integration:** API-05/API-03/API-09.
- **Acceptance:** a sale prints a correct receipt offline with a gap-free number; a reprint is
  audited.

## M31-FR-03 — Email / SMS / WhatsApp / push routing, consent and delivery status
- **Shall:** route notifications across email/SMS/WhatsApp/push, respecting consent, with
  delivery status.
- **Actors/scope:** CRM (M21), all modules needing to notify. **Preconditions:** consent
  (M16-FR-02); provider connectors (M32); `⟳ AVR-15` (consent practices).
- **Flow:** a notification request → **consent + frequency check** → routed via provider →
  delivery status tracked. **Alt/error:** a send breaching consent/frequency is **blocked**
  (not warned-and-sent).
- **Rules:** **consent-safe by construction** (PRV, M21-FR-01); provider policy (WhatsApp
  templates); delivery status recorded.
- **Permissions:** governed. **Offline:** sends are online; queued if provider down (retry, FR-04).
- **Audit/privacy:** every send audited against consent state. **Integration:** API-11; M32
  connectors; durable broker (§30.2).
- **Acceptance:** a notification to a non-consented customer is blocked; delivery status is
  visible.

## M31-FR-04 — Retry, suppression, cost and template approval controls
- **Shall:** control retry, suppression (do-not-contact), messaging cost and template approval.
- **Actors/scope:** CRM/Platform admin. **Preconditions:** routing (FR-03).
- **Flow:** failed sends retry with backoff → poison → **dead-letter (visible, never dropped,
  #6)** → suppression lists honoured → cost tracked/capped → templates approved before use.
  **Alt/error:** over-budget messaging halts per policy.
- **Rules:** retry + **dead-letter** (like the sync outbox / Tally, hard rule #6); suppression
  absolute; templates approved (§28).
- **Permissions (§28):** template approval; budget caps. **Offline:** online.
- **Audit/privacy:** retries/suppression/cost audited. **Integration:** API-11.
- **Acceptance:** a poison notification lands in a visible dead-letter (not lost); a
  suppressed contact is never messaged; an unapproved template cannot send.

## Module acceptance & test families
- Versioned templates + retained immutable documents; offline receipt generation with
  gap-free numbers; consent-safe routing (blocked on breach); retry/dead-letter/suppression/
  template-approval.
