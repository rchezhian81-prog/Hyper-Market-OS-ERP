# M32 — Integration and developer platform

- **Priority:** P0/P1 · **Release:** R1 · **Stage:** 5/7 · **Roadmap:** §5 M32, §16 D14, §30 (API/events), §31, §35
- **Purpose:** The safe seams between us and the outside world — versioned APIs, durable messaging with idempotency and dead-letter, a connector SDK, and the adapters for Tally, payments, GST, messaging, logistics and hardware. **No secrets in code** (hard rule #4, guardrail); **no undocumented direct DB writes** (§35).

## M32-FR-01 — Versioned APIs, OAuth/service identities, webhooks, idempotency
- **Shall:** expose versioned APIs (API-01…API-13) with OAuth/service identities, signed webhooks, and idempotency/concurrency control.
- **Actors/scope:** internal apps, external partners, Platform Admin. **Preconditions:** IAM (M02).
- **Flow:** define versioned contract (OpenAPI/AsyncAPI) → authenticate via OAuth/service identity + scopes → serve with idempotency keys and version checks → emit signed webhooks. **Alt/error:** replayed request → one effect (idempotent); version-conflict rejected; unsigned/replayed webhook rejected.
- **Rules:** semantic versioning + deprecation policy (§30.1); **backward compatibility for supported store versions** (mobile-safety, A-10); idempotency keys stored (§29.1); scopes carry branch/tenant claims.
- **Permissions (§28):** scoped service identities; least privilege. **Offline (§31):** edge consumes cached contracts; store queues sync via these APIs.
- **Audit/privacy:** API/auth events audited; correlation IDs. **Integration/reporting:** the API catalogue itself; usage metrics (FR-03).
- **Acceptance:** a replayed API call produces one business effect; an unsupported version is rejected cleanly; webhooks are signed and replay-protected.

## M32-FR-02 — Connector SDK, mapping, throttling, retry, dead-letter
- **Shall:** provide a connector SDK with mapping, throttling, retry and dead-letter queues for all integrations.
- **Actors/scope:** Platform/integration developers. **Preconditions:** message broker (§19 baseline).
- **Flow:** build a connector from the SDK → map fields → apply throttle/retry → poison messages go to a **visible dead-letter** workflow. **Alt/error:** dead-letter items remain visible, owned, reconcilable — **an operator cannot delete evidence** (§31.1, hard rule #6).
- **Rules:** idempotency, ordering rules, retry and dead-letter mandatory (§19 messaging baseline); connectors are versioned.
- **Permissions (§28):** connector config by Platform Admin. **Offline (§31):** durable outbox/inbox at the edge (§19 store edge).
- **Audit/privacy:** connector activity and dead-letters audited. **Integration/reporting:** API-11; queue-depth and dead-letter reports.
- **Acceptance:** a poison message lands in a visible dead-letter queue and cannot be deleted by an operator; retries are bounded; a connector upgrade doesn't break in-flight messages.

## M32-FR-03 — Sandbox, API documentation, secrets, usage monitoring
- **Shall:** provide a sandbox, published API docs, managed secrets, and usage monitoring.
- **Actors/scope:** developers, partners, Security Admin. **Preconditions:** APIs (FR-01).
- **Flow:** publish docs + sandbox → issue scoped credentials from a **managed vault** → monitor usage/rate. **Alt/error:** a leaked/rotated secret is revoked; abnormal usage alerts.
- **Rules:** **secrets live in a managed vault, never in repo/image/log** (hard rule #4, SEC-04, guardrail); rotation and emergency revocation documented (§19.1).
- **Permissions (§28):** secret access least-privilege and audited. **Offline (§31):** edge holds minimized, rotated credentials.
- **Audit/privacy:** secret access and usage audited. **Integration/reporting:** API-11; usage/rate reports.
- **Acceptance:** no secret appears in the repository (guardrail + secret-scan in CI); a credential can be rotated and revoked; sandbox lets a partner integrate without production data.

## M32-FR-04 — Tally, payments, GST, messaging, logistics, hardware adapters
- **Shall:** provide certified adapters for Tally, payments/UPI, the GST/e-invoice ecosystem, WhatsApp/SMS/email/push, maps/logistics and store hardware.
- **Actors/scope:** integration developers, Platform Admin. **Preconditions:** SDK (FR-02), provider accounts `⟳ AVR-10/AVR-14`.
- **Flow:** configure each adapter with credentials + mapping → certified device/provider matrix (D14) → monitor health. **Alt/error:** provider outage → queue/fallback; uncertified device blocked.
- **Rules:** payments via **RBI-authorized provider with tokenization** (§35, hard rule #3); messaging respects consent/template approval (M31); hardware on a certified matrix (§33).
- **Permissions (§28):** adapter config by Platform Admin. **Offline (§31):** hardware adapters run at the edge (LAN-first); cloud adapters queue.
- **Audit/privacy:** adapter config/health audited; no card data (hard rule #3). **Integration/reporting:** API-11; integration-health report (feeds M35).
- **Acceptance:** the Tally adapter posts idempotently with a dead-letter (ties M23); the payment adapter uses a verified RBI provider and stores no card data; an uncertified peripheral is blocked.

## Module acceptance & test families
- Idempotent APIs; signed/replay-safe webhooks; visible non-deletable dead-letter; **no secret in repo** (guardrail + CI); consumer-driven contract tests (§30.1); certified device/provider matrix.
