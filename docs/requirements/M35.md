# M35 — Backup, disaster recovery and observability

- **Priority:** P0 · **Release:** R1 · **Stage:** 5 · **Roadmap:** §5 M35, §32 (RPO/RTO), §35, §31, NFR-10
- **Purpose:** The reason you can recover on the one evening it matters — encrypted immutable backups with a **proven restore**, defined RPO/RTO, and full observability (metrics, logs, traces, sync lag) with owned alerts. Built in Stage 5 before any feature (Annexure H).

## M35-FR-01 — Encrypted scheduled backups, immutable/off-site copy, restore tests
- **Shall:** take encrypted scheduled backups with an immutable off-site copy, and regularly test restores.
- **Actors/scope:** Platform/Security Admin, Owner (witness). **Preconditions:** environments (Stage 5).
- **Flow:** schedule encrypted backups → replicate to immutable off-site → **perform a real restore and reconcile** → document in the restore runbook. **Alt/error:** a failed backup/restore alerts immediately; ransomware isolation path exists (§35).
- **Rules:** **immutable off-site copy; no single-device backup** (§33 hardware); restore is proven, not assumed (Stage 5 gate: do not proceed until a restore has actually been performed); recovery reconciles counts/values/hashes **without editing original evidence** (§4.2).
- **Permissions (§28):** backup/restore by admin; audited. **Offline (§31):** store-edge has its own backup; RPO 0 for committed local sales (§32).
- **Audit/privacy:** backup/restore events audited; `BackupVerified/Failed` (§30.2). **Integration/reporting:** API-11; backup/restore status.
- **Acceptance:** a test database is destroyed and **restored while the owner watches** (Stage 5 owner check); backups are encrypted and off-site; a failed backup alerts.

## M35-FR-02 — RPO/RTO, store/cloud recovery, business-continuity runbooks
- **Shall:** define and meet RPO/RTO per service, with store and cloud recovery and business-continuity runbooks.
- **Actors/scope:** Architecture/Platform, Owner. **Preconditions:** backups (FR-01).
- **Flow:** set RPO/RTO targets → build recovery + failover → rehearse (drills) → keep runbooks current. **Alt/error:** a drill that misses target raises a remediation.
- **Rules:** **RPO 0 for committed local sales; store service RTO ≤ 30 min; cloud RPO ≤ 15 min, RTO ≤ 4 h** (§32 targets); runbooks written so a non-programmer can follow at 9pm (Annexure H).
- **Permissions (§28):** recovery by admin. **Offline (§31):** store keeps trading during cloud recovery (P-01).
- **Audit/privacy:** drills and outcomes recorded. **Integration/reporting:** API-11; RPO/RTO and drill reports.
- **Acceptance:** a store-recovery drill meets the ≤30-min target; committed local sales are not lost (RPO 0); the runbook is followable by a non-programmer.

## M35-FR-03 — Metrics, logs, traces, sync lag, queue and integration health
- **Shall:** provide observability — metrics, structured logs, traces, sync lag, queue depth and integration health.
- **Actors/scope:** Platform/Operations, Owner (freshness). **Preconditions:** services emitting telemetry.
- **Flow:** collect metrics/logs/traces → surface sync lag, queue depth, integration and device health → feed owner freshness (M29). **Alt/error:** a stalled queue or growing sync lag raises an alert (P-08 no silent failure).
- **Rules:** **sync lag, stale data and reconciliation differences are visible** (P-08); no sensitive secrets/payment data in logs (SEC, hard rule #3/#4).
- **Permissions (§28):** ops scope. **Offline (§31):** edge telemetry buffered and shown; freshness surfaced.
- **Audit/privacy:** no PII/secrets in logs (guardrail-aligned). **Integration/reporting:** API-11; health dashboards.
- **Acceptance:** growing sync lag or a stalled dead-letter queue raises a visible alert; logs contain no card data or secrets; the owner can see data freshness.

## M35-FR-04 — Alert ownership, escalation, incident/postmortem, capacity planning
- **Shall:** assign alert ownership and escalation, run incident/postmortem discipline, and plan capacity.
- **Actors/scope:** Operations/Security, Owner. **Preconditions:** observability (FR-03).
- **Flow:** alert fires → routed to a named owner → escalates if unacknowledged → incident managed → postmortem → capacity reviewed. **Alt/error:** an unacknowledged critical alert escalates (≤15 min ack target, §32).
- **Rules:** every alert has a **named owner** (P-03/NFR-09); **CERT-In 6-hour incident-reporting workflow** where applicable (§35, compliance C-05); capacity sized for 2× peak with headroom (§32).
- **Permissions (§28):** incident roles defined. **Offline (§31):** store continues; incidents tracked online.
- **Audit/privacy:** incidents/postmortems recorded (M34). **Integration/reporting:** API-11; incident and capacity reports.
- **Acceptance:** a critical alert reaches its named owner and escalates if unacknowledged; a security incident triggers the CERT-In 6-hour workflow; capacity headroom is reported.
