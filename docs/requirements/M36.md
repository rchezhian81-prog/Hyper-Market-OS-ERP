# M36 — Multi-tenant platform, white-label and developer ecosystem

- **Priority:** P0/P1 · **Release:** R8 · **Roadmap:** §5 M36, §16 D12/D14, §7 (platform). **Decision:** OB-01 / **ADR-0003** (commercial, multi-tenant product).
- **Purpose:** Turn SRE Retail OS into a **commercial product many retailers use** — hard tenant isolation, plans/entitlements/metering, **white-label configuration without code forks**, tenant lifecycle (export/closure/upgrade), and a partner/developer ecosystem. Builds directly on the tenant foundation already in code (`packages/tenant` entitlements + settings, `packages/config`).

> Appendix B records; `⟳ AVR-##` marks store facts; §5 cross-cutting inherited. The
> from-the-start posture (isolation, config-driven, no hard-coded store facts) is already
> live (ADR-0003); this module is the **full commercial-SaaS layer** on that base.

## M36-FR-01 — Tenant isolation, plans, entitlements, metering, subscription readiness
- **Shall:** isolate each tenant's data and configuration, and manage plans, feature
  entitlements, usage metering and subscription readiness.
- **Actors/scope:** Platform Admin (SRE as the vendor), tenant admins. **Preconditions:**
  the tenant model (ADR-0003; `packages/tenant`).
- **Flow:** create tenant → assign plan → entitlements enable modules → meter usage →
  (future) bill. **Alt/error:** **cross-tenant access is blocked** (critical, §35);
  requesting a feature outside the plan is denied.
- **Rules:** **hard tenant isolation** — every record/query is `tenant_id`-scoped (ADR-0003);
  optional features are **default-off** entitlements; usage metered per tenant.
- **Permissions (§28):** platform admin manages tenants; a tenant admin manages only within
  its tenant. **Offline (§31):** the platform plane is online; a store edge keeps trading
  regardless (P-01).
- **Audit/privacy:** tenant lifecycle and entitlement changes audited (M34). **Integration:**
  API-11/API-13; implemented on `packages/tenant` (`Entitlements`) + `packages/config`
  (per-tenant settings).
- **Acceptance:** no query returns another tenant's data; a tenant sees only its entitled
  modules; usage is metered per tenant.

## M36-FR-02 — White-label / configuration without code forks
- **Shall:** let each tenant brand and configure the product (name, logo, theme,
  terminology, document/receipt templates) **without any code fork**.
- **Actors/scope:** Platform/tenant admin. **Preconditions:** per-tenant config
  (`packages/config`), document templates (M31).
- **Flow:** tenant sets branding + templates in config → the same deployment renders that
  tenant's brand. **Alt/error:** an unset brand falls back to a neutral default.
- **Rules:** **one codebase, one deployment, many brands** (M36-FR-02); branding is
  configuration, never a fork (P-06, OD-09).
- **Permissions:** tenant admin within limits; platform admin sets bounds. **Offline:**
  branding cached in the signed edge pack.
- **Audit/privacy:** branding changes audited/versioned (M01-FR-03). **Integration:** API-11.
- **Acceptance:** two tenants show visibly different branding and receipt templates from a
  single codebase and deployment — no fork.

## M36-FR-03 — Tenant export, closure, support boundaries, upgrade compatibility
- **Shall:** export a tenant's data, close/offboard a tenant, enforce support-access
  boundaries, and keep upgrades backward-compatible.
- **Actors/scope:** Platform admin, tenant admin. **Preconditions:** tenant isolation
  (FR-01); retention policy.
- **Flow:** tenant requests export → full dataset exported (portable formats) → on closure,
  access revoked, legally-required records retained, rest removed per policy. **Alt/error:**
  closure blocked while obligations (e.g. tax retention) remain.
- **Rules:** **a tenant owns and can export its data** (OD-09, P-06); support access is
  **time-bound and audited** (M33); **upgrades are backward-compatible** (versioned APIs,
  no breaking a live tenant).
- **Permissions (§28):** closure is governed/approved. **Offline:** export/closure online.
- **Audit/privacy:** export, closure and support sessions audited (M34); **never delete
  audit evidence** (#6). **Integration:** API-11/API-12.
- **Acceptance:** a tenant's full data exports; closure revokes access and retains
  legally-required records; an upgrade does not break an existing tenant.

## M36-FR-04 — Partner implementation and developer ecosystem
- **Shall:** enable partners/developers to implement and extend the product via versioned
  APIs, a connector SDK, a sandbox and documentation.
- **Actors/scope:** Partners/developers, platform admin. **Preconditions:** versioned API
  surface (M32; `docs/api/catalogue.md`).
- **Flow:** partner gets a **sandbox tenant** + versioned API/SDK + docs → builds an
  integration → certified → runs against production tenants. **Alt/error:** an unversioned/
  breaking change is rejected (deprecation window required).
- **Rules:** **versioned APIs and contracts** (P-06, M32); connector SDK; sandbox isolated
  from production (hard rule #7); documented data models.
- **Permissions:** partner access scoped and audited. **Offline:** developer plane online.
- **Audit/privacy:** partner access/usage audited. **Integration:** API-01…13, API-13 (AI).
- **Acceptance:** a partner builds an integration against the sandbox using versioned APIs,
  with no SRE code change, and it runs unchanged against a production tenant.

## Module acceptance & test families
- Tenant isolation (no cross-tenant leakage — the critical test); entitlement gating;
  white-label from config (no fork); tenant export/closure with retention; upgrade
  backward-compatibility; sandbox/API versioning.
