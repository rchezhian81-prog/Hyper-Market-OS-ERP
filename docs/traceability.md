# Traceability

Traces every requirement from design through to a passing test and the release it
shipped in. Part of the Definition of Done in `CLAUDE.md`.

The roadmap (§37) provides a **family-level** baseline proving every requirement
family has an implementation route. **Stage 2 expands this to one row per
individual requirement** (`M##-FR-##`, `D##-FR-##`, `SEC-##`, `PRV-##`, `AI-NFR-##`,
`MG-##`, etc.) with design, code, automated-test and release references. No
requirement may reach **Done** without a complete individual row.

| Count verification (§34, OB-06, MG-06, §28) | `packages/migration/src/count-verification.ts` | Proving the extracted stock against the shelves — the only thing that can. **Value-stratified**, not random: the high-value lines are a CENSUS, the tail is sampled, because a random sample that happens to miss the ghee has verified almost nothing while looking thorough. Refuses a sample chosen by whoever ran the extraction (§28); the expected quantity never reaches the count sheet (`expectedQtyShownToCounter: false`); the draw is seeded so an auditor can ask why THIS line. The extrapolation is labelled an **estimate** and returns `undefined` rather than a fabricated figure when the sample cannot support one. Tested in `tests/unit/migration-count-verification.test.ts` |
| Verification report (§34, OB-06, MG-06, QG-07, P-08) | `packages/migration/src/verification-report.ts` | The one page the owner and the CA sign, gathering all six checks into the language of the runbook. The most dangerous file in the migration, because **a report is what people believe** — nobody re-derives a figure once a signed page exists — so the refusals are about the document rather than the arithmetic. **It cannot be produced from some of the domains**: four of twelve renders perfectly, every heading filled, and is a complete-looking account of a third of the business, so nothing renders until every domain has a finding. **An unproved domain is a row in the same table in the same type**, never a footnote (P-08). **A proved domain that states no limit is refused** — every check has a real limit, and a blank is read by whoever signs as "no limit". **Each exception is accepted one at a time, by name, by the owner, with a reason**, and a reason that fills the box without saying anything is refused as `packages/migration/src/cutover.ts` refuses a non-explanation. Whoever ran the extraction can neither prepare nor sign it (QG-07). Signatures accumulate and are never replaced — a signature belongs to the figures that were on the page when it was given. Renders Indian money grouping, every witness rather than the first, and counts where the domain is not a rupee total. Worked example in `docs/evidence/example-verification-report.md`; tested in `tests/unit/migration-verification-report.test.ts` |
| **OB-06 verification gate** (§34, OB-06, MG-06, QG-07) | `tests/integration/every-figure-has-a-witness.test.ts` | All six outside-evidence checks run as **one pass over one shop**, against real PostgreSQL 16.13. Adds the two things unit tests structurally cannot: it **walks the `VERIFIES` table for all twelve domains and proves every named source has a module behind it** — catching a domain with a named witness and no code, which is what a migration under time pressure produces; and it **proves the witnesses agree with each other**, tying four figures across checks (bank gross = filed taxable + tax; signed Stock = the counted shelves; signed Creditors = the suppliers' own confirmations; signed GST payable = the filed return), so a wrong number must be wrong consistently in two independent records to survive. The gate is proved to **fail**: withhold the physical count and five domains are refused by name as `verified_by_the_same_system`. The structural check is enforced by `Record<ExternalSource, string>`, so adding a kind of evidence with no check built is a **compile error**, not merely a red test. Verified figures are banked as append-only events carrying the witness that proved them. 16 assertions |
| Loyalty verification (§34, OB-06, MG-06, M12, §28) | `packages/migration/src/loyalty-verification.ts` | The last of the six and the odd one out: **no third party keeps a record of a customer's points**, so the only witness is the customer. Two facts about customers decide the design. **The feedback is asymmetric, so complaints are a useless sample** — a customer whose points fell complains, one whose points rose never does, so a sample drawn from complaints is 100% shortfalls by construction and would confirm a systematically over-crediting migration with real evidence from real customers. **Refused by name.** And **the loud direction is not the dangerous one**: understated points are visible, immediate and self-correcting because they generate complaints; overstated points are silent, permanent, redeemed in goods at our cost, and never discovered — so the silent side sorts first, is valued at the tenant's own cost per redeemed point, and is never netted against the loud side. The central control mirrors the stock count: **the balance is never shown to the customer** (`balanceShownToTheCustomer: false`), because asked *"is it 450?"* almost anybody says yes — what is accepted is the customer's own figure or the activity they remember. Sampling is seeded and three-strata (largest balances, tier boundaries, random tail), with the census winning over the boundary rule so coverage is never double-counted. Tier changes are named — a tier is on every receipt. `provesTheBalanceWasEarned` is typed as the literal `false`. Tested in `tests/unit/migration-loyalty-verification.test.ts` |
| Books verification (§34, OB-06, MG-06, M16) | `packages/migration/src/books-verification.ts` | The signed closing balance sheet **is** the opening position, so this ties the other five checks together — stock, debtors, creditors, cash and tax all appear on it, each already proved by its own evidence. Also, stated plainly, **the weakest of the six as independent evidence**: the CA prepared them from the same old system, so what they add is a professional signature and the discipline of double entry, not an independent source (`provesTheAccountsAreRight: false`). **A balancing figure is refused by name** — Suspense, Opening Difference, Diff A/c, plug — because posting the difference there makes the books balance and be wrong, and that account is never cleared. Checked **before** the balance test, so a book that closes only because of the plug is never reported as balancing. Also refused: draft (unsigned) accounts; accounts that do not themselves balance; a cutover that is not the day after the accounts' period end (out by a whole trading period while looking authoritative); and the absence of what **only the CA has** — depreciation, provisions, accruals, prepayments, drawings — whose absence is not a variance but exactly the amount that would end up in suspense. Contra accounts (drawings, accumulated depreciation) are known, so the wrong-side flag does not fire on every correct set of books. Tested in `tests/unit/migration-books-verification.test.ts` |
| Tax verification (§34, OB-06, MG-06, M23) | `packages/migration/src/tax-verification.ts` | The only check that runs **backwards**: a filed return is true as a matter of law, so the question is not whether it agrees with the books but what the books must become. Four refusals, each load-bearing: **no acknowledgement reference** — a spreadsheet named after a return is a working paper, and the ARN is the only thing separating filed from prepared; **not a whole tax period** — a part period is short by design and reads as missing sales; **superseded by an amendment** — reconciling to the restated original gives a wrong answer with a flawless audit trail; **the return's own arithmetic failing** — reconciling to it would spread the error through every opening figure. **A slab rate is never inferred from a total**: an average across a mixed basket is not a rate anything could have been sold at, so a books line off the statutory slabs is refused, and no entry point taking a total and a rate exists (proven by scanning the module's real exports). GSTR-1 is checked against GSTR-3B as well as against the books, because the department reconciles those two automatically — a difference there is **inherited, not created**. A difference against a filed return is a **disclosure to the CA**, not a private data fix. `provesTaxWasCorrectlyCharged` is typed as the literal `false`. Tested in `tests/unit/migration-tax-verification.test.ts` |
| Banking verification (§34, OB-06, MG-06, §29.1) | `packages/migration/src/banking-verification.ts` | Sales proved against the bank, which has no interest in agreeing with our old ERP. Neither `packages/reconciliation` (needs a shared provider reference) nor `packages/settlement` (needs the provider's own file) can answer this for a historic period, so the route is **reconstructed**: cash lodged in lumps days later, card net of commission and the GST on it, UPI gross on its own cycle. The control the module stands on — **a commission rate is declared, never derived.** A rate computed as `(gross − banked) / gross` makes every shortfall commission by definition, so the check agrees perfectly at any figure; a test demonstrates a 60,000 hole reconciling to zero under a fitted rate, and the same input refused under `derived_from_the_difference`. **Cash is the dangerous direction** — the only tender a person carries, and the only difference with no counterparty who will ever chase it, so it carries its own figure plus the peak standing unlodged. **An unexplained credit is an exception, not a bonus**: migrated as revenue it overstates turnover and the tax due. The statement's span is read off its header, not inferred from its lines, and must run **past** the period end or the last day's batch is missing while the dates look matched. `provesSalesWereComplete` is typed as the literal `false`. Tested in `tests/unit/migration-banking-verification.test.ts` |
| Supplier reconciliation (§34, OB-06, MG-06) | `packages/migration/src/supplier-reconciliation.ts` | The external check that needs **nobody's goodwill** — the supplier keeps their own ledger and will confirm it, because they want paying. Two ledgers with no shared key that were never meant to agree at a point in time, so the job is telling a **timing difference** from a real one: within the window a payment in transit is the ordinary explanation, and past it, it is not. An `amount_differs` item is **never** timing, because both sides hold the document. Three rules that do not bend: **the dangerous direction is theirs** — an invoice only on their statement is a liability we would migrate as zero, so it is called out separately and sorted first; **nothing is netted**, because an unapplied payment and an unrecorded credit of the same size produce a clean zero that hides both; and **signs are mirrored deliberately** — every item carries its contribution to *theirs minus ours*, so the items sum to the headline difference and a reversed side cannot balance at twice the true figure. A supplier who never replied is named, not counted as agreeing. Tested in `tests/unit/migration-supplier-reconciliation.test.ts` |
| Export completeness (§34, OB-06, MG-01/05, P-08) | `packages/migration/src/completeness.ts` | The failure that RECONCILES PERFECTLY — a paginated grid exports one page, the file parses cleanly, its own grand total agrees to the paisa, and it holds 4,000 of 41,200 products. Four signals in order of trust: a row count taken off the screen; **`Page N of M`, which works when nobody wrote anything down**; the end marker, available only for a file that would have had one; and sequence density, deduped so repeats cannot inflate it. **Refused, not flagged.** `unverifiable` is a distinct verdict from `complete` — a file with no signals has failed to be caught, not passed. `compareDoubleKeyed` is Route D's control. Tested in `tests/unit/migration-completeness.test.ts` |
| Self-extraction round trip (§34, OB-06, MG-05) | `packages/migration/src/render-report.ts` | Renders a KNOWN dataset back into a printed report — banner, page breaks, repeated headers, department subtotals, Indian digit grouping — so the parser is measured against ground truth rather than against whether the answer looks plausible. `checkRoundTrip` names the product that went missing rather than counting rows short, and compares as a MULTISET so a lost second location cannot hide behind a still-present id. Proven end to end in `tests/integration/we-get-it-out-ourselves.test.ts`; tested in `tests/unit/migration-render-report.test.ts` |
| Legacy report parsing (§34, OB-06, §29.1) | `packages/migration/src/report-parser.ts` | What these systems ACTUALLY export — a printed page in a spreadsheet. Finds the header rather than assuming line 1; classifies subtotals FIRST so a group total is never counted as data (the misread that doubles a department); **Indian digit grouping** (4,12,000 is twelve lakh); **no float anywhere** — the decimal part is parsed as text, because `parseFloat(x)*100` turns 19.99 into 1998.9999999999998; `CR` read as negative so supplier balances keep their sign; a lone `-` read as nil. Nothing dropped silently, banner rows included. Tested in `tests/unit/migration-report-parser.test.ts` |
| Legacy self-extraction (§34, OB-06) | `packages/migration/src/extraction.ts` | **MG-01/02/06 without vendor cooperation** — four routes ranked by what they structurally lose, re-keying refused as a migration source because it cannot be re-run; and the control the approach stands on: a domain verified only against the system it came from is **refused by name**, so every total is proved against outside evidence (bank, filed returns, supplier statement, physical count). Procedure in `docs/runbooks/legacy-self-extraction.md`; tested in `tests/unit/migration-extraction.test.ts` |
